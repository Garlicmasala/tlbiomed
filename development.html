About this document. This guide covers the development side of T&L@Biomed: the principles that shaped the architecture, the BDD/TDD/smoke workflow, the commit history and how the project grew, the test suite design, code metrics, architecture decision records, environment quirks, and the deployment pipeline. It is meant for anyone who wants to understand how the site is built and why each decision was made, and for future contributors who need to extend it.

1. Development philosophy

The project was built against five non-negotiable constraints that drove every technical decision:

  1. Zero cost. No paid hosting, no paid domain, no paid dependencies — everything must run on free tiers.
  2. Zero backend. No server, database, or serverless functions — the artifact must be deployable to any static host by copying one file.
  3. Zero build step. No bundler, transpiler, or framework CLI — what you see in index.html is what runs in the browser.
  4. Portable & extensible. Content lives in a plain config object; adding a note, question, or grade year is a data edit, not a code change.
  5. Verified before deploy. A BDD/TDD/smoke suite must pass on every change; a typo cannot reach students.

These constraints ruled out React/Vue/Svelte (build step), Next.js/Nuxt (backend), CMS platforms (lock-in + cost), and database-backed solutions. The result is a single self-contained HTML file with vanilla JS, tested in Node, deployed to static hosting.

3. Development workflow (BDD / TDD / Smoke)

Every change follows the same loop. The three test categories serve different purposes:

  • BDD (config.behavior) — 20 tests that assert the content is well-formed: every quiz question has a valid answer and unique ID, grade counts sum to their cohort, all links are real URLs, the passcode and language config are valid. These describe the expected behavior of the published data.
  • TDD (quiz, grades, i18n) — 18 tests that assert the pure logic is correct: answer evaluation, score computation, band sorting (A+ > A > … > F), grade statistics, shuffle non-mutation, duration formatting, translation lookup and placeholder substitution. These were written alongside (or before) the logic they test.
  • Smoke — 18 tests that assert the shipped artifact is intact: single self-contained file, locked ECharts CDN with SRI, allowed font mirror only, no emoji, no ES modules, all interactive element IDs present, and the same checks for paper.html. These catch regressions that logic tests cannot.

5.1 How the sandbox works

The core script is extracted from index.html between /* ===APP-CORE-START=== */ and /* ===APP-CORE-END=== */ markers, then executed inside a Node vm sandbox with a minimal window object and document: undefined. The script's DOM initialization is guarded (if (typeof document !== "undefined" ...)), so it runs safely without a browser. The sandbox exposes window.TL — the pure-logic API — which the tests call directly:

// tests/helpers/extract.js (simplified)
const code = html.slice(start, end);
const sandbox = { window: {}, document: undefined, console, setTimeout, clearTimeout };
vm.createContext(sandbox);
vm.runInContext(code, sandbox);
return sandbox.window.TL;  // evaluateQuestion, computeScore, gradeStats, bandSort, t, fmt, ...

8. Architecture decision records

ADR-01: Single self-contained HTML file Accepted

Decision: The entire site — markup, styles, logic, config, i18n — lives in one index.html.

Why: Zero build step, zero dependency installation, trivial deployment (copy one file), trivial backup, and the instructor can open it in any text editor. The tradeoff — a large file (~126 KB) — is acceptable for a course hub of this scale.

ADR-02: Vanilla JavaScript, no framework Accepted

Decision: No React, Vue, Svelte, or jQuery — plain ES2017 with DOM APIs.

Why: No transpiler, no bundler, no version churn, no security advisories from nested dependencies. The site's interactivity (quiz, filters, toggles) is well within what vanilla JS handles cleanly. The pure-logic core is decoupled from the DOM so it can be tested in Node.

ADR-03: Client-side passcode gate (not real security) Accepted with caveat

Decision: Private sections (notes, grades, tutorials) are gated by a passcode checked in JavaScript.

Why: Zero backend, zero cost. The passcode stops casual browsing by students who shouldn't see grades or unreleased notes. Caveat: Anyone who views the page source can read the passcode and all content. This is explicitly documented as a light gate, not real security — suitable for class materials, not for sensitive data.

ADR-04: ECharts via jsDelivr with SRI Accepted

Decision: The only JavaScript dependency is ECharts 5.6.0, loaded from jsDelivr with a fixed version and Subresource Integrity (SRI) hash.

Why: ECharts is the most capable free charting library for the grade distribution view. Pinning the version and verifying the SRI hash prevents supply-chain attacks — if the CDN file changes even one byte, the browser refuses to execute it. No other JS libraries are loaded.

ADR-05: Node built-in test runner, zero test dependencies Accepted

Decision: Tests use node:test and node:assert — no Jest, Mocha, Vitest, or any test framework.

Why: Node 18+ includes a capable test runner and assertion library. Zero test dependencies means zero node_modules bloat, zero supply-chain risk in the test chain, and npm test works immediately with no install. The vm module lets the core logic run in a sandbox without a browser or jsdom.

ADR-06: GitHub Pages via Actions (primary) Accepted

Decision: Primary deployment is GitHub Pages via the included Actions workflow (git push → automatic deploy). Netlify Drop was the original fallback for quick previews; its anonymous deploys were suspended in September 2026, so GitHub Pages is the only maintained path.

Why: Both are free. GitHub Pages gives automatic deployment on every push (matching the instructor's "I'll update quiz and grades when needed" workflow) and never expires. Netlify Drop used to give instant preview URLs without a GitHub account, but anonymous drops expired after 1 hour, were rate-limited, and the service suspended them entirely in September 2026 — preview only, never permanence.

ADR-07: Hash-based routing, no router library Accepted

Decision: Views are plain <section data-route> blocks shown and hidden by a small hash router; the tab bar and the GATED list decide which views need the passcode.

Why: Zero dependencies, no server rewrites on any static host, and deep links (#notes, #quiz) survive refresh and sharing.

ADR-08: Topic & difficulty live in the question data Accepted

Decision: Each question carries topic and difficulty; the filter chips and the topic·difficulty tag are derived from the bank at render time.

Why: The UI cannot drift from the data — adding a question with a new topic automatically adds its chip and tag, and removing the last question of a topic removes both.

ADR-09: Flat i18n dictionary with parity tests Accepted

Decision: All UI strings live in one flat LANGS object (163 keys per language at HEAD); lookups fall back English → raw key.

Why: A missing or mistyped key fails the i18n suite instead of the page; adding a language is appending one dictionary with the same keys.

ADR-10: Attempt history in localStorage Accepted

Decision: Best score and attempt count persist per device in localStorage behind a try/catch (private mode), and never leave the browser.

Why: Zero backend and zero privacy surface — no analytics, no accounts, nothing stored server-side; history is per student device by design.

ADR-11: Pages artifact is the site root Accepted

Decision: The workflow uploads . (the site root) as the Pages artifact. upload-pages-artifact accepts exactly one path, so a curated file list is not possible without an intermediate staging step.

Why: Simplicity wins over a tidy artifact: the repo is public, so serving README.md, CHANGELOG.md and tests/ alongside the three HTML pages costs nothing and adds no risk.

ADR-12: Token-based visual design with dark mode Accepted

Decision: All colours, spacing and type live in CSS custom properties; a light/dark theme toggle flips the token set, and ECharts re-renders with a dark-aware palette.

Why: A lab/medical green palette keeps the hub calm and readable in lecture contexts; tokens make restyling a data edit, and the theme preference persists per device with zero backend.

ADR-13: Accessibility-first chrome Accepted

Decision: Tabs use ARIA roles (role="tab" / role="tabpanel" + aria-selected); the quiz is keyboard-complete (1–4 select, Enter submit); a print stylesheet hides chrome; prefers-reduced-motion disables animations.

Why: The site is used in lecture theatres and on any student device; keyboard and print paths cost little code but widen who can actually use it. No emoji and a restrained palette keep it classroom-appropriate.

9. Development environment & quirks

The project was developed on Windows (PowerShell). A few environment-specific quirks are worth documenting for future contributors:

  • PowerShell curl alias. PowerShell aliases curl to Invoke-WebRequest, which has different flags. Use curl.exe explicitly for curl-style commands.
  • Inline Node scripts with regex. Passing JavaScript with regex or special characters via node -e "..." in PowerShell frequently mangles quotes and parentheses. Write a temp .js file and run it instead.
  • CRLF/LF. Git on Windows may convert LF to CRLF on checkout (warning: LF will be replaced by CRLF). This is cosmetic and doesn't affect the site, but it inflates file byte counts slightly.
  • PowerShell has no &&. Chain commands with ; or separate tool calls; a compound line that uses && fails to parse.
  • $HOME is read-only in PowerShell. It is an automatic variable — use another name (e.g. $h1) for your own paths.
  • git push writes progress to stderr. PowerShell renders it as a red NativeCommandError and reports exit 1 even on success — look for the old..new main -> main line to confirm the push actually landed.
  • Edit/Write tool timeouts. On Windows, the file edit/write tools occasionally time out (likely antivirus scanning large HTML files). When this happens, writing a Node patch script and running it via Bash is a reliable fallback.
  • Netlify anonymous Drop limits (historical). Anonymous (unclaimed) Netlify Drop sites expired after 1 hour and were subject to a daily upload limit. As of September 2026 the service suspends anonymous deploys and CAPTCHA-gates the upload page, so this path is no longer usable.
  • Browser automation iframe. Netlify Drop's file input lives inside a storage.html iframe — the automation had to target that iframe before uploading (moot since Drop is suspended; kept for history).

10. Extending the project

10.1 Adding content

All content is in SITE_CONFIG at the top of index.html. Adding a note, question, or grade year is a data edit — no code changes needed. After editing, run npm test to verify the content is well-formed (valid answer, counts sum to cohort, real URLs), then commit and push.

10.2 Adding a language

Add a new dictionary to LANGS with the same 163 keys as en. The i18n test suite automatically verifies key parity — if a key is missing, the test fails. Update SITE_CONFIG.language if the new language should be a default or auto-detected.

10.3 Adding a feature

  1. Add the pure logic to the core script (inside the APP-CORE markers) if it's testable without DOM.
  2. Add a test in the appropriate suite (quiz.test.js, grades.test.js, etc.).
  3. Add the DOM wiring and markup.
  4. Add the element ID to the smoke test's interactive elements list.
  5. Run npm test — all 56+ must pass.
  6. Update paper.html and this document if the feature is significant.

10.4 Adding a tab

Add a new <section class="view hidden" data-route="newtab"> in the markup, add a corresponding .tab button with data-route="newtab", add the route to the ROUTES array, and add it to GATED if it should be passcode-protected. The hash router handles the rest automatically.

11. Deployment pipeline

The included workflow (.github/workflows/deploy.yml) triggers on every push to main and on manual workflow_dispatch. It uses actions/configure-pages@v5, upload-pages-artifact@v3 (uploading ./index.html), and deploy-pages@v4. No build step is required — the artifact is the site root.

12. Deployment incident postmortem (2026-09-08)

What happened. The site had been previewed through Netlify Drop. On 2026-09-08, Drop suspended the anonymous preview (This site is suspended) and its upload page started serving a CAPTCHA, ending the anonymous path — which had always expired after ~1 hour and carried a daily upload limit.

Migration. The project moved to GitHub Pages. Three workflow runs tell the story:

CommitOutcomeFix
74e89d0Stuck at Setup Pages — Pages not enabled for the repoSettings → Pages → Source: GitHub Actions (done in the browser)
7e78938Stuck at Upload artifact — upload-pages-artifact rejects a multi-line path listArtifact path changed from a three-file list to the site root
1485931Success — live at garlicmasala.github.io/tlbiomed/—

Lessons. (1) Verify Pages is enabled before debugging the workflow itself. (2) upload-pages-artifact takes exactly one path — for a curated artifact, stage files into a temp directory and upload that. (3) Push-to-deploy means the instructor's update loop is just: edit SITE_CONFIG → npm test → git push.
