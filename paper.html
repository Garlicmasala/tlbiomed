Abstract. T&L@Biomed is a static course hub built for a university biomedicine teaching context. It delivers five sections — lecture notes, an interactive multiple-choice mock quiz, past grade distributions, structured tutorials, and a study guide — inside a single self-contained index.html with no server, database, build step, or paid dependency. Private sections are gated by a client-side passcode; the quiz provides instant correct/wrong feedback, a timer, keyboard shortcuts, answer shuffling, and per-device attempt history, and a retry-wrong-only mode; grade data is rendered as an interactive ECharts bar chart with chart/table and counts/percent toggles and one-click print; a site-wide search box finds notes and tutorials in one dropdown. The entire UI is bilingual (English and Traditional Chinese) with browser-language auto-detection. Quality is enforced by a 56-test BDD/TDD/smoke suite running in Node's built-in test runner, and deployment is a single git push via GitHub Actions. This paper documents the architecture, configuration, data model, internationalization, testing strategy, sample data, and deployment pipeline.

1. Project overview & constraints

The site was built against a set of hard constraints set by the course instructor:

  • Free. No paid hosting, no paid domain (a custom domain may be added later if enrolment grows).
  • Zero backend. No server, database, or serverless functions — the artifact must be deployable to any static host.
  • Single file. One index.html containing markup, styles, logic, and configuration, so updates are a one-file edit.
  • Portable & extensible. No framework, no build step, no lock-in; content lives in a plain SITE_CONFIG object.
  • Private-by-default for sensitive content. Notes, grades, and tutorials are passcode-gated; the mock quiz is public.
  • Interactive. The quiz must give instant correct/wrong feedback; grades should be explorable rather than a static image.
  • Verified. BDD/TDD/smoke tests must pass before every deploy.

These constraints ruled out full-stack frameworks, CMS platforms, and database-backed solutions, and pointed directly at a static single-file architecture with client-side logic.

2. Architecture

The entire application is one HTML file organized into five clearly separated layers, plus two locked external dependencies. A pure-logic core is deliberately decoupled from the DOM so it can be executed inside a Node vm sandbox and unit-tested without a browser.

Layer responsibilities. SITE_CONFIG is the single source of truth for all published content (notes, quiz, grades, tutorials) and settings (passcode, language). LANGS holds every UI string in both languages. The pure-logic core (window.TL) contains only deterministic functions — scoring, grade statistics, band sorting, array shuffling, duration formatting, and translation lookups — with no DOM access. The DOM layer wires that logic to the five views, handles routing (hash-based), theme and language toggles, and the passcode gate. CSS is a token-based design system with light/dark variants. All markup is static HTML; dynamic lists are rendered by the DOM layer from config.

3.1 Cross-cutting features

  • Passcode gate. Notes, grades, and tutorials require a shared passcode; the quiz is always public. Unlock state persists in localStorage; a footer button re-locks.
  • Dark mode. CSS-variable theme toggle, persisted per device; ECharts re-renders with a dark-aware palette.
  • Bilingual UI. English and Traditional Chinese, auto-detected from navigator.language, switchable from the footer, persisted.
  • Toasts & copy-link. Non-blocking notifications for unlock, lock, theme, language, and clipboard actions.
  • Site-wide search. A search box in the tab bar finds matching notes and tutorial items in a single dropdown, grouped by section, with direct links.
  • Retry wrong only. After a quiz attempt, students can re-attempt just the questions they missed — focused revision.
  • Topic filter & difficulty. A chip row filters the question pool by any of the 19 subjects; every question shows a topic·difficulty tag while answering.
  • Print grades. One-click print/PDF export of the grade distribution; print CSS hides navigation and chrome.
  • Responsive & reduced-motion. Mobile layout collapses the DNA masthead and hides keyboard hints; prefers-reduced-motion disables animations.

4. Configuration & data model

All publishable content lives in SITE_CONFIG at the top of index.html. No code changes are needed to update the course — only data edits, followed by npm test and a deploy.

Sample flag convention. Every built-in content entry carries sample: true. While any sample flag remains, a yellow banner reminds the instructor to replace the content. Deleting the flags silences the banner automatically — no separate toggle needed.

5. Internationalization

The UI chrome (not the course content, which the instructor authors in their chosen language) is fully translated. Strings live in a flat LANGS dictionary; adding a third language means appending one dictionary with the same keys. Translation lookups fall back English → the raw key, so a missing string never crashes the page.

Figure 3 — i18n key coverage: 163 keys per language, 100% parity between English and Traditional Chinese (326 total strings).

Mechanics. Static elements carry data-i18n (or data-i18n-ph for placeholders) and are re-rendered on language switch. Dynamic strings (question counters, verdicts, stat chips, toasts) use a t(key) / fmt(key, vars) pair with {placeholder} substitution. Initial language is read from localStorage, then auto-detected from the browser (zh-* → 中文), then the configured default. The choice is persisted and the document title and meta description update with it.

6. Testing & quality assurance

The project follows a BDD/TDD/smoke discipline with zero test dependencies — Node's built-in node:test runner and vm module are sufficient. The core script is extracted between /* ===APP-CORE-START=== */ and /* ===APP-CORE-END=== */ markers and executed in a sandbox, exposing window.TL for direct assertion. This means every logic function the page runs is tested without a browser.

Figure 4 — Distribution of the 56 automated tests across five suites (config.behavior 20, smoke 18, quiz 9, grades 5, i18n 4).

6.1 What the suites guard

  • config.behavior (20 tests) — every quiz question is well-formed with a valid answer and unique ID; grade counts sum to their stated cohort; all links are real http(s) URLs; passcode and language config are valid; sample bank has ≥8 questions.
  • smoke (18 tests) — single-file self-containment, locked ECharts CDN with SRI, allowed font mirror only, no emoji, no scrollIntoView / ES modules, all interactive element IDs present, pure-logic API exposed.
  • quiz (9 tests) — answer evaluation, score computation to one decimal, band sorting (A+ > A > A- > … > F), Fisher–Yates shuffle non-mutation, duration formatting.
  • grades (5 tests) — per-year statistics (total, pass, fail, pass rate, mode band), band ordering, fail-band handling.
  • i18n (4 tests) — EN→ZH key parity, safe fallback, placeholder substitution in both languages, and that every data-i18n key used in markup exists in both dictionaries.

8. Deployment pipeline

The site is fully static and deploys to any static host. The recommended path is GitHub Pages via the included GitHub Actions workflow — every push to main builds and publishes automatically, matching the instructor's "I'll update quiz and grades when needed" workflow.

The workflow (.github/workflows/deploy.yml) uses actions/configure-pages@v5, upload-pages-artifact@v3 (uploading the site root), and deploy-pages@v4, triggered on every push to main and on manual workflow_dispatch. No build step is required.

Deployment migration (2026-09-08). The site was originally previewed through Netlify Drop. On 2026-09-08 the service suspended the anonymous preview (This site is suspended) and began CAPTCHA-gating its upload page, so the project moved to GitHub Pages. The workflow needed three iterations: first it uploaded a three-file list (upload-pages-artifact rejects multi-path inputs), then Pages was enabled with Source: GitHub Actions, and finally the artifact path was set to the site root — which is also why README.md and the tests/ folder are served alongside the three HTML pages (harmless on a public repo). Every push since then deploys in about a minute.

9. Security & limitations

  • Passcode is a light gate, not real security. It stops casual browsing, but the passcode and all private content are visible in the page source. Suitable for class materials; do not put truly sensitive data behind it.
  • Client-side only. Quiz results and attempt history live in the student's own localStorage; no analytics, no tracking, no data leaves the browser.
  • Dependency whitelist. Only two external resources load: ECharts from jsDelivr with a fixed version and SRI integrity hash, and fonts from the miaoda.feishu.cn mirror. No other CDNs, no analytics, no polyfill.io.
  • Anonymous hosting expiry. Netlify Drop's anonymous deploys (hourly expiry, daily upload limits) were suspended in September 2026 and its upload page is now CAPTCHA-gated; GitHub Pages is the permanent path.
  • Grade chart colour ramp. Supports up to 5 years before cycling; keep "All years" views within that range.

10. Roadmap

  • Quiz modes. Timed auto-submit and multiple-answer questions (retry-wrong-only revision is already live).
  • Difficulty practice. Filter the quiz by difficulty band (basic / intermediate / advanced) and review per band.
  • Grade import. A small CSV-paste utility to populate SITE_CONFIG.grades.years without hand-editing JSON.
  • More languages. The LANGS dictionary is flat — Simplified Chinese and other languages are a single dictionary away.
  • Passcode hardening. The gate is source-readable by design; a hash check would close that, at the cost of a tiny static build step.
